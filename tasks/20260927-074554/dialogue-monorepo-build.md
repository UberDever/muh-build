# Dialogue: generic build system for the C monorepo

## Glossary (user, 2026-09-27)

- Workspace = monorepo: the directory holding all projects (`~/dev/c`; earlier called M or `REPO_PATH`). Not a git repo.
- Repo = a project or library = one git repo, `<workspace>/<project>`.
- Earlier entries use `REPO_PATH` and "whole-repo"; read them as workspace.

## Framing

- Question: what the generic build system for `~/dev/c` looks like, as the user pictures it.
- Mode (user, 2026-09-27): the user describes; the agent takes notes and asks clarifications only. Design review later.

## Model (user's picture, as stated)

Setting: siblings `P/` (a project), `L/` (a library), `MB/` (muh-build). P wants to use L. We know how to build both; the tool is the manifest.

- Manifest contents (user): system lib deps, vendored lib deps, commands to compile/build/link, configurations and modes. It also says how to install; installation is dictated by install prefixes.
- Proposition (user): configurations and modes are adjustable by custom flags. Idea first, design later.
- Proposition (user): the CLI flags (`-p`, `-t`, ...) unify into those custom flags. The user passes an arbitrary Lua term through the shell to configure anything; the build tool accepts only a manifest.
- First hurdle (user): to use L, P must know where L's artifacts are and what they are. Could come from the existing targets mechanism: L provides a Lua term describing anything about its targets.
- Proposition (user): the user-facing interface and the machine interface are the same, Lua terms; only formatting may differ. Prose for trivia, Lua terms for structured data.
- Confirmed (user, 2026-09-27): the restatement of points 1, 2, 3 and 5 (setting; the manifest describes a project completely; one input channel, a Lua term; one language for people and machines).
- Clarification (user): L's description lives in its manifest. A project knows its targets, how to build and deploy them; this is fairly static. Some entries are dynamic: which objects and how many, include flags, and so on. To be clarified.
- Clarification (user): the shell term overrides the manifest, like `-DCMAKE_X=1`. Both are records, so the override is deep: a union of records with the provided term dominant.
- Clarification (user): commands stay functions; terms are their parameters; the manifest is the default parameter body, since it is always one big record.

### Discovery (user, 2026-09-27)

- Each project may have `muh-build.mod`, like `go.mod`: a Lua term listing the libraries P uses. Per entry: the git commit hash, the manifest, and the build parameter term.
- Location is always a monorepo: M is the directory containing MB. Everything is discovered from M and appended onto it: include flags, install flags, asset locations.
- Workflow: P's mod file has an L entry (hash, manifest, `{}` term). Building P builds L first: MB goes into L, builds it and installs it by L's manifest.
- Installation leaves `use.lua` at the install prefix: a record P can `dofile`. It is the protocol for integrating projects: objects, scripts, assets, whatever the consumer needs. It exists once the project is built.
- Physical layout: building P creates a git worktree of L at the wanted hash; install output goes there too. Worktree name `for-<project-name>`, easy to gitignore. Different projects can use the same L at different versions.
- Open (user asks the agent for guidance): place the checkout as `M/L-<hash>/` or keep it inside `L/`.
- Clarification (user): checkouts are keyed by consumer, since the consumer's term can override the dependency's build settings. M is the parent directory of MB. `use.lua` is generated by MB; L lists what goes into it, like today's `install_rules`. Dependencies are recursive: a tree.

### Recursive build (user, 2026-09-27)

- To use L you inevitably use L's dependencies. Only a parent configures its direct children; nothing configures a grandchild. "The vassal of my vassal is not my vassal."
- L is built with its own mod file.
- The worktree is created on the dependency's side: what a project wants is placed where it is got from. The nominal name records who asked for it.
- P has revisions of its own, so the name is `for-<project>-<hash>`, e.g. `L/for-P-abcd1234/`. Stale ones may pile up as junk; accepted.
- What this gives (user): clear ownership and lifetime separation.
- Correction (user): L may build K differently depending on the arguments P or Q pass to L. Then `K/for-L-<hash>` can differ per consumer of L. Open (agent): the checkout name `for-L-<L's hash>` does not capture L's received arguments.
- Clarification (user): the hash in `for-<project>-<hash>` is some commit hash; no preference which. Open (agent): builds from a dirty tree.
- Direction (user): static builds preferred, so transitive dependencies come for free. Some include flags and artifacts must be inherited through a mechanism; it looks like a unification of the `use.lua` terms. Undecided: shared versus static decides deployment.
- (user) Diamonds (P uses K@h1 and L, L uses K@h2) can happen. Result: as when linking two versions of a library, a link error at best. Sane approach: never reach it; internal linkage; never use a dependency's dependencies, even by accident. How to mitigate: unknown; the user wants to know. Crux for the review.
- Proposal (user): name checkouts by a hash of the received term too: its string representation through crc32 or similar. Open (agent): Lua table iteration order is unspecified, so the representation must be canonical (for example, sorted keys) for the hash to be stable.
- (user) Go's single-version selection appeals: simple and sane. The user asked for its drawbacks.
- Clarification (user): MB on P's side merges the `use.lua` records of L and K; L's record cannot contain K's, since both are dynamic.

### Actual build (user, 2026-09-27)

- Correction (user): `use.lua` comes from the configure step (today's `MuhCmake` step), not from the build.
- Process: build the dependency tree, sort it topologically, then build in that order, reusing libraries already built at the same hashes.
- Result: `for-P-...` checkouts in L1..LN, and `for-Lk-...` checkouts in their own dependencies. On reaching P, it has every include path, link flag and asset flag (if any, passed by `-D` or similar), enough to build and link the executable.
- Clarification (user): reusing a checkout means rerunning its build; it is quick when nothing changed. No fifth part.
- (user) Go's way could be copied: a project's commits are its versions, ordered. Breaking API is the `.../v2` case; how to do that in C is unclear, maybe a separate project.
- Proposal (user, 2026-09-27): small and medium projects list all dependencies flatly, including dependencies of dependencies. Assumes builds can run in parallel and no library needs another library built as an artifact. Motive: avoid the transitivity hole, "it is slippy". The user asks whether it could work.
- [fact] (agent) The fixture's manifest gives SDL3 consumers an include directory inside SDL3's build output (`SDL3_OUT/include-revision`, `tests/muh-game/manifest.debug.linux.lua:184`): a header its consumers need is generated by its build.

### Workspace model (agent proposal on user request, 2026-09-27)

- (user) Back-out question: what developers of small heterogeneous pet projects do for reuse. Agent survey: vendoring, single-header libs, sibling paths, submodules, fetch-at-configure, system install, package managers. The user has tried them all.
- (user) Composing several manifests into one project build is possible in principle. Going lower: the root is `REPO_PATH`; every project is `REPO_PATH/<project>`, always. The user asked the agent to think it through as the developer of the whole repo.
- Agreed (user, 2026-09-27) from the agent's picture: (1) one include root `-I$REPO_PATH`, includes name the project; (2) packages are directories, `public/` includable from any project, `internal/` from its own, `cmd/` executables, checked from depfiles; (3) the dependency graph comes from includes, no mod file, `public/` is the interface; (5) one workspace build, one compile database; (6) shared vendored third-party code at the top.
- (user) On (4): not only HEAD; other commits too, thought imperatively.
- (user) On flags: say how per-project toolchain and flag deviations work, imperatively.
- Decision (user, 2026-09-27): publishing one project alone is install. Install produces a real hermetic installation; the implementation must respect that meaning.
- (agent proposal, 2026-09-27) Point 4 made imperative: builds compile against a view, `build/views/<hash>/root/<project>` symlinks to a working tree or to a shared worktree at a pinned commit; the view is a term `{mode, projects = {X = {rev, ...}}}`. Flags in three scopes: per file (merged workspace, owning manifest, view override), per link (one per view: sanitizers, LTO, toolchain), per interface (`public_defines` propagated to includers). Objects cached by project, revision and effective-flags hash. Install: binaries, or `public/` headers of the closure in `<project>/public/` shape plus archives plus a small `P.lua`; hermeticity checked by a test compile against the prefix alone.
- (user) Question: so this is a whole-repo snapshot mechanism. (agent) Yes: a multi-repo snapshot, a vector of commits plus configuration; only fully pinned views are snapshots, `working` entries make a selection. Prior art: Android `repo` manifests, Zephyr `west.yml`.

### Imperative project-level builds (user, 2026-09-27)

- (user) "Imperative" meant: conceptually a plain script (`cc`, `ar`, `cp`) could build the whole workspace into the needed project. Proposal: work at the level of repos, not files, and keep it imperative: `L1.checkout(abcd1234)`, `L1.build(WS/build/L1-for-P1, flags)`, `P1.build(WS/build/P1, manifest)`. No declarations, rules or overrides; a pure sequence of steps. Inside a repo, muh-build keeps its file graph and caches.
- (agent) Thoughts: the split puts caching where it pays (files) and control where it pays (repos). It dissolves the depfile, cross-view cache, generated-header and view-path objections. Addition proposed: `build` returns a Lua record (include dirs, archives, public defines) passed to later calls as `deps`; `use.lua`-like files only at install. Nested calls replace the dependency tree; a repo can export its own build function. Costs: repetition across repos, silent diamonds (guard: memoize `build` on repo, rev and flags), sequential by default, no global graph for list and clean. Needs: MB as a module returning targets; manifests accepting `deps`.
- Proposed test (agent): scratch workspace with two repos; one script pins L1, builds it, builds P1 against the result, through today's MB CLI.
- Accepted (user, 2026-09-27): the costs listed (repetition, sequential, no global graph) are fine at small scale.
- Decision (user, 2026-09-27): abandon transitivity completely. There are only leaves: a project that wants something built writes how, fully, in its own script. Repetition is accepted ("in the LLM era, it's fine"). Rejected: repos exporting build functions that others call (the agent's nested-recipe addition), since it hides builds, e.g. a second K, from the caller.
- Confirmed (user): each repo's manifest still describes how to build its own files; the script picks repos, revisions, flags, deps and order. A project still needs a public API.
- Confirmed (user): "L1 needs K" lives in L1's script and again in P1's, maintained by hand, unchecked; intended. L1 is sometimes its own thing.
- Direction (user, 2026-09-27): no installation for libraries: "what for?" The interest is actual projects and apps.
- Decision (user, 2026-09-27): a project's public API is both the `public/` directory convention (sources, includable from any repo) and the record `build` returns (include dirs, archives, defines), shaped by what the manifest exports.
- Clarification (user): libraries generally are not installed, but may be; nothing forbids it. Installable leaves are generally few.

### Experiment (agent, 2026-09-27; artifacts in experiment-2026-09-27/)

- Naming (user asked to prevent collisions); tested proposal (agent): `<ws>/build/<project>/<repo>@<rev>-<hash of canonical term>/` with `src/<repo>` and `out/`.
- [fact] A (P1, dev+ASan; K pinned v1; L1 working tree with an uncommitted edit; L3 pinned with `L3_WIDE`, defines passed on): works. Output `k_value=1 l1_calc=15 sizeof(l3_pt)=24`, both `y` reads 42.
- [fact] B (A without passing L3's defines to P1): ASan SEGV; `l3_make` writes a 24-byte struct into P1's 8-byte one. Interface defines must travel in the record.
- [fact] C (P2, release; K with a generated header; L2 pinned against it): works once K's manifest exports `include_dirs = {"build/gen"}` and the record carries them. Output `K_VERSION=2 k_value=2 k_twice(1)=1002 l2_calc=200`.
- [fact] D (L2 built against K v1, P2 links K v1 and K v2): no error; every K symbol came from the first archive; K v2 silently absent. With order K v2, L2, K v1 and a main using only `k_twice`: `k_twice` from v2 and `k_value` from v1 in one binary, no error. The linker pulls archive members independently.
- [fact] E (rerun of A unchanged): 50 ms, 0 compiles, 0 links.
- [fact] F (projects F1 and F2 build K's working tree with different flags): archives separate; the generation step ran once and F2 reused F1's output (same source directory through the symlink, sentinel present); the real K repo gained an untracked `build/`.
- [fact] Old pins carry old manifests: after the manifest protocol changed (`include_root` to `include_roots`), pinning L2 at its old revision failed inside L2's own old manifest.
- [fact] muh-build gaps met: crash without `cmd/` (`build.lua:559`) or without `internal/` (`build.lua:529`); a library-only repo builds nothing by default (defaults are `cmd:` and `test:`); `vendor:` steps run only as link dependencies of executables; vendor outputs resolve from the project root and ignore `-p`, so they land in the source tree.
- [fact] Passing the term by environment variable prevents loading a manifest in-process with a term; the helper read exports in a subprocess.
- Not tested: a wrong archive order on the link line (the scripts listed dependents before dependencies).
- (agent) Reading: the flat-script model held for every scenario; what broke was muh-build's single-repo assumptions and paths written into sources. Standing: diamonds are silent at link time; the manifest protocol needs stability across pinned revisions; working-tree builds share one source directory.

- Decision (user, 2026-09-27): manifest versioning on both sides: the manifest declares its version; the user of the manifest passes the expected version in the term it gives to muh-build.

## Objections

- (user, 2026-09-27) Fear that the workspace model breaks somewhere.
- Standing (agent, against own proposal): the first build has no depfiles, so the graph, link lines and `public_defines` are unknown on a clean build; needs a scan pass (`cc -M`) or declared dependencies.
- Standing (agent): the object cache key misses the revisions of included repos' headers; stale objects shared across views.
- Standing (agent): generated headers (e.g. SDL3 `include-revision`) cannot be found from includes; vendored builds need explicit ordering.
- Standing (agent): symlinked view roots leak into `__FILE__`, debug info and `compile_commands.json`; editing a pinned repo through clangd edits a throwaway worktree.
- Standing (agent): worktrees register in each repo's `.git`; deleting `build/` leaves stale entries until `git worktree prune`; submodules need care.
- Standing (agent): per-link flags must reach vendored builds (cmake); TSan and MSan break on uninstrumented code.
- Proposed test (agent): a spike with two tiny repos and one view (P live, L pinned), checking depfiles, the compile database and a clean first build.

## Decision

Closed 2026-09-29 (user+agent). No formal review phase was held; the design was settled step by step
through the experiment, the integration suite and the user's rulings, recorded above and in the dated
notes (2026-09-27.md, 2026-09-29.md, platforms.md).

Decided:
- A workspace of sibling repos; each project has a flat, imperative recipe; no transitivity (only leaves).
- A recipe declares `requires`: (repo, name, revision, expected manifest version, params); inputs are
  validated before anything runs, outputs are not.
- Every repo, vendored ones included, has its own manifest; external builds run in preconfigure.
- Manifests list their packages in link order; `public/` and `internal/` packages; uniform includes
  `"<repo>/public/<pkg>/api.h"`.
- Public interface: `public/` plus the build record (include dirs, interface defines, archives).
- Shared builds in `<workspace>/build/<repo>@<rev>-<hash>/`, identified by revision, manifest (text,
  for working), params and dependency builds; each holds build-info.lua. One compile database per project.
- A diamond is the programmer's fault; one repo twice in a link is refused.
- Stock Lua; a portable host interface (Linux now; macOS and Windows planned).

Rejected: mod files and `use.lua` (for flat recipes); recipes exporting build functions (hide builds);
manifests naming dependencies; command hashing (overkill); a force switch; lfs.

Revisit when: a second platform host is written (case of paths, 20260929-103900); builds get slow
(parallel builds, noted as an idea).
